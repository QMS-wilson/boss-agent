四、优化一：数据库连接复用

改动前

每执行一个操作就新建一条数据库连接，用完立即关闭。建连（TCP + 登录握手）稳态约 25ms， 而一条轻查询本身只需要 13ms —— 超过一半的时间花在"开门"上。

改动后

改为线程本地连接池：每个工作线程持有一条长连接反复使用。

  • 为什么用线程本地而非共享连接池：生产环境线程数固定（快池 8 + 重池 2）， 每线程持一条连接就已吃满并发度，不需要借还协议 —— 那类池最容易在异常路径上漏掉连接。
  • 连接标识必须包含数据库名：账套可按请求切换，标识漏掉库名会导致 静默串账（拿 A 账套的连接去读 B 账套的数据）—— 这是本项目最不能犯的错。
  • 语义与改动前完全一致，所有调用点零改动。

★ 唯一真风险的封堵：应用锁残留

风险：单据取号用的应用锁是会话级的，不随事务提交/回滚释放。 如果某条异常路径漏了释放，这把锁会挂在被复用的连接上， 用这条连接的下一个请求就永远拿不到号 —— 症状是「这家客户忽然再也开不了单」。

处理：不再依赖调用方自觉，而是在取号/放号函数内部自己记账：

  • 取到锁 → 登记；释放锁 → 无论成败都销账（释放报错时锁大概率已不在， 继续记账反而会把正常连接误判为不可用）。
  • 归还连接前做最后一道检查：账上还有欠锁 → 直接丢弃这条连接 （连接关闭时 SQL Server 会自动释放该会话的全部锁，这是最可靠的兜底）。

五、优化二：商品查询排序改写（收益最大）

问题

商品查询为了让「停用」的商品排在最后，排序键里用了一个条件表达式：

ORDER BY CASE WHEN 停用 THEN 0 ELSE 1 END, 商品编号

而商品表的主索引恰好就是按「商品编号」建的 —— 加了条件表达式之后， 数据库无法再使用这个索引排序，退化成对全部 48,584 行做排序。

排序写法耗时倍数
直接按商品编号排序（走索引）1.0 ms1×
带条件表达式排序（现状）48.7 ms49×

商品查询是开单页选货的第一屏，用户每敲一个字都会触发。

改法：把排序条件拆成两段查询

非停用商品（按编号排序，走索引）
        UNION ALL
停用商品  （按编号排序，走索引）

两段各自都能走索引，合起来的效果与原排序完全等价 —— 因为原排序的语义本就是「先按是否停用分组、组内按编号」。

这是"等价改写"而不是"近似" —— 这是它安全的关键。 保序验证 100% 通过：7 档翻页位置 × 4 组搜索关键字， 逐页逐行比对，0 处差异。

六、一个被证伪的优化（重要教训）

背景：单据列表的双键排序（按日期、再按行号）耗时 62ms， 而只按日期排序只要 0.6ms —— 差 100 倍。原因同样是第二排序键不在索引里。

尝试：先用单键（日期）快速定位这一页的日期边界，再在缩窄后的范围内做双键排序。 实测确实快（60ms → 1.2ms），性能提升 50 倍。

但它被立即证伪了：

  • 单键序与双键序在跨日期的补录单上结果正好相反。 数据库实证：编号 36667 的日期是 09-21（补录单），编号 36668 的日期是 09-19（补录单）； 双键序把 36668 排在前面（因为编号大），单键序把 09-21 排在前面（因为日期新）。
  • 实测 4 档翻页位置，整页全部错位。

最危险的地方：如果只对比「前 1000 条」这种截断结果，会显示 "完全一致" —— 因为差异只出现在被截断的位置附近。 必须逐页比对完整结果，比对截断结果会掩盖问题。

结论：代码已回退。已把完整的证伪过程写进源码注释，防止以后有人再走这条路。

八、结论与建议

承载能力结论

当前系统完全满足「4~5 个 App 同时登录开单」的需求，且有 8 倍以上余量。
  • 实测 40 个并发客户端、443 个请求，0 失败。
  • 并发增加时延迟保持恒定，没有互相拖慢。
  • 报表等重操作被隔离在独立线程池，不影响开单和查询。
  • 单据取号在 8 路并发下严格连号（用户硬性要求已满足）。
