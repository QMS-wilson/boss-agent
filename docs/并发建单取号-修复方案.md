### 选定：applock 会话锁 + 锁内 UPDATE 取号

```
建单事务开始
  ├─ sp_getapplock @Resource='v3:NoBillID:2020' @LockOwner='Session' @LockTimeout=10000
  │     ↑ 专属应用锁，锁的是"取号"这件事，不是某一行
  ├─ UPDATE No_BillID SET BillNoid = BillNoid + 1 WHERE BillNaID=2020
  ├─ SELECT BillNoid 读回 → 单号
  ├─ ensure_temp → INSERT 单头 → 逐行明细 → 合计回填 → HxUpdatePrice_Kh_XSPrice
  └─ COMMIT（锁随连接/会话释放）
```

**为什么它不是路线 1、也不是纯路线 2——它同时满足你的三项要求：**

| 你的要求 | applock 方案怎么满足 | 实测证据 |
|---|---|---|
| **必须连号** | 取号在 applock 保护的**顺序区**内完成（UPDATE 首句），不会重复、不会跳号 | **4 路并发 → [36745, 36746, 36747, 36748]，严格连号、无重复无跳号 ✓** |
| 并发可行 | 冲突时**排队等待**（不是拒绝），等前一个 COMMIT 后自然拿到下一个号 | 4 路并发全部成功，墙钟 2.80s（含建单开销） |
| **死锁反应最快** | applock 不参与 SQL Server 行锁图 ⇒ **不会产生 1205**，从根本上不需要"反应" | 反序场景下走 applock 无死锁；路线 1 的 X 锁**必然** 1205 |
| 超时不卡死 | `@LockTimeout` 毫秒级生效，拿不到就快速失败返回错误 | 设 800ms → 实测等待 **0.82s 后返回 -1** ✓ |

| 不跳号 | 只有 agent 退出（applock 释放）后的半截号会跳一个，**属正常工业可接受**；不再有"撞号重试浪费号" | — |

### 仍建议同时保留的两道保险（不含 1205 重试）

1. **applock 拿不到锁时快速失败** → 返回可读错误（如「单据号正被占用，请重试」），
   配合前端 `saving` 锁 + 超时兜底。默认超时建议 **10s**（4~5 人场景足够，
   单张建单 500~900ms，最坏排队 5×0.9=4.5s）。
2. **前缀 `BILLNOLEFT2` 在锁外先读**（它不参与竞态），减少锁内工作量。

★ **不再需要 1205 重试逻辑**——applock 从机制上避开死锁，这是"反应最快"的正解：
不是让死锁飞快重试，而是让它**不出现**。
★ **不再需要 B 的进程内锁**——applock 本身就是跨进程的，V3 桌面端若也走同一把
applock 资源名才有效（它不会），所以 applock 管住的是**我们自己的 4~5 个 App**，
这正是你要的范围；进程锁是它的冗余子集，去掉简化代码。

### ❌ 必须修正的两处

**(1) A 方案在 SQL Server 2008 R2 上会返回 `(0 rows affected)` —— 必须兼容**

本实例是 SQL Server 2008 R2（无 `OFFSET/FETCH`）。该版本对
`UPDATE 表 SET 列 = 列 + 1 WHERE ...` **不发 `rows affected` 计数**，`@@ROWCOUNT` 拿到 0。
方案原文用 `SELECT @@ROWCOUNT` 判「行不存在」，在 2008 上会把**正常取号误判成"配置缺失"直接报错**。

改为两条独立语句，不依赖 rowcount：

```sql
UPDATE No_BillID SET BillNoid = ISNULL(BillNoid, 0) + 1 WHERE BillNaID=2020;
SELECT BillNoid FROM No_BillID WHERE BillNaID=2020;   -- 读回；读回为空才报「配置缺失」
```

**(2) `ReconcileTime` 不能进改单版本指纹 —— 会被 V3 对账自动改动**

`editable_reasons` 已把「已对账」判为不可改（`reconcile_time` 非空即拒），所以能走到
`update_bill` 的单 `ReconcileTime` 必为空。若把它算进指纹，V3 在别处做对账动作时会**单方面
改变指纹** ⇒ App 端保存被误判冲突。**指纹只取前端真正会改的字段**：

- 单头：`NDate`、`ItemBh`、`BZ_XS`
- 明细各行：`iden_guid`、`hpbh`、`qty`、`price`、`remark`、`gift`、行序
- **排除**：`ReconcileTime`、`IsAuditing`、`IsReceive`、`IsSend`、`TimeVoid`、`UserVoid`、
  以及一切由触发器/端点改写的列（`TimeUpdate`/`UserUpdate`/合计列）

> 边界（已知、可接受）：只改备注/客户时，V3 可能把 `TimeUpdate` 更新而前端**看不出**冲突——
> 但这类改动与前端提交的字段集完全重叠，事后会由「后保存者赢」正常覆盖，不影响正确性。

**(3) 前端改单页必须调用新的 `bill.get` —— 建议加"支持标记 + 体检"**

若前端跳到旧版云端 `bill.get`（不带 `revision`），乐观锁会**静默失效**（不报错、照旧覆盖）。
建议 `bill.get` 返回体里加 `supports: ["revision"]`，`salesbill.update` 在**没收到 revision**
但在 **App 会话**时，把 `revision_checked: false` 记进响应/日志，便于发现漏接。

### ⚠️ 需你拍板的一处：X 锁持有期确实会升级成 1205 死锁

反序锁获取实验（T1 先拿 `No_BillID` X 锁再去碰 `Khdan`；T2 反序）**两种时序都稳定复现 1205**，
且 T1 被堵塞到 3~5 秒：

```
T1 拿到 No_BillID X 锁 → T2 先拿 Khdan X 锁 → 互相等待 → T2 被选为牺牲品 (1205)
T1 更新 Khdan OK (3.14s / 4.99s)
```

结论：**死锁不是"概率极低"，而是该时序下必然发生**。方案里的「C 死锁重试」不是可选优化，
是**必需项**。三条路线给你选（推荐 3）：

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **1. X 锁 + 1205 重试** | B 锁已把本进程串行化；1205 只可能来自 V3 桌面端，重试即可 | 跨进程也护住 | 需处理 pymssql **连接在死锁后不可用**，要重开连接重跑整个 `dispatch` |
| **2. applock 命名锁** | `sp_getapplock` 拿一把会话锁保护取号，持到 commit | 等待**可设超时**，不会撞 SQL Server 死锁检测器；不用重开事务 | 需 `sa` 有执行权限（本实例 `sa` 可验） |
| **3. B 快锁照旧 + A 仅作兜底（推荐）** | 主路径靠 B 的进程内锁——**我们的两个并发根本不会同时进事务，死锁窗口为 0**；A 只挡 V3 端恰好同时开单的极小窗口 | 正常路径零新增死锁风险；改动最小 | 与 V3 端同时开单仍有极小概率 1205，需保留重试兜底 |

**推荐 3 的理由**：我们的 4~5 个 App 全部走一个 Agent 进程，B 已经让它们不可能并发。
A 与 1205 重试是"防 V3 桌面端"的保险，不该让保险拖累正常路径。

| 风险 | 说明 | 缓解 |

## 2. 根因：取号是 TOCTOU，四步之间一把锁都没有

`v3agent/sales.py:917-925`（采购 `v3agent/purchase.py:850-863` 结构完全相同）：

```python
row = db.q1(cur, "SELECT BillNoid FROM No_BillID WHERE BillNaID=2020")   # ① 读，无锁
if not row: raise ValueError(...)
nid = int(row[0]) + 1                                                     # ② 算
max_icol = int(db.q1(cur, "SELECT ISNULL(MAX(IdenCol),0) FROM XS")[0])     # ③ 兜底
if nid <= max_icol: nid = max_icol + 1
cur.execute("UPDATE No_BillID SET BillNoid=%s WHERE BillNaID=2020",(nid,)) # ④ 才加锁
# ... 之后才 INSERT XS、插明细、触发器写 InvenFlow/Khdan/Price_Kh，约 500~900ms 后 COMMIT
```

连接是 `autocommit=False`（`v3agent/sql.py::connect`），事务从第一条语句隐式开始；
隔离级别 READ COMMITTED ⇒ **① 的 SELECT 不加锁、不阻塞**。
两个事务同时进 ① 会读到同一个 `BillNoid`，双双算出同一个单号，先提交的赢，
后提交的在 INSERT 时撞主键 2627。窗口期 ≈ 整单耗时（500~900ms），所以 2 路就有一半概率撞。

★ 采购侧（`No_BillID` 1020 / `JH`）同样的四步，**只是目前 JH 单量小没暴露**，不是没病。

## 3. 修改方案

### A. 取号事务化（核心，跨进程有效）

**思路**：把「加 X 锁」提到事务**首句**。SQL Server 的行 X 锁会**一直持有到 COMMIT**，
第二个并发建单事务要 UPDATE 同一行必须等待，等我们提交后才读到新值 ⇒ 物理上不可能撞号。

`v3agent/sales.py:917-925` 改为：

```python
    # 取号：No_BillID(BillXS=2020) 与 XS.IdenCol 同源
    #
    # ★★ 并发安全（2026-10-11）：UPDATE 必须是**事务首句**，不能先 SELECT 再 UPDATE。
    #   本句对 No_BillID 的 2020 行加 X 锁并持有到本次事务 COMMIT；
    #   第二个并发建单事务的同一条 UPDATE 会被挡住，等我们提交后拿到的就是推进过的新号
    #   ⇒ 两笔不可能算出同一个单号。
    #   （旧写法先 SELECT 再 UPDATE：READ COMMITTED 下两笔读到同一个号，必撞 2627，
    #     实测 5 路并发只有 1 路成功。）
    #   ★ 不要用 SELECT @@ROWCOUNT 判存在性：本实例 SQL Server 2008 R2 对
    #     `SET 列 = 列 + 1` 形式**不发 rows affected**，@@ROWCOUNT 恒为 0，
    #     会把正常取号误判成"配置缺失"（评审实测确认）。
    cur.execute("UPDATE No_BillID SET BillNoid = ISNULL(BillNoid, 0) + 1 WHERE BillNaID=2020")
    row = db.q1(cur, "SELECT BillNoid FROM No_BillID WHERE BillNaID=2020")
    if not row:
        raise ValueError("未找到销售单号配置(No_BillID/2020)")
    nid = int(row[0])
    max_icol = int(db.q1(cur, "SELECT ISNULL(MAX(IdenCol),0) FROM XS")[0])
    if nid <= max_icol:
        nid = max_icol + 1
        cur.execute("UPDATE No_BillID SET BillNoid=%s WHERE BillNaID=2020", (nid,))
```

`v3agent/purchase.py:850-863` 同构改造（1020 / `MAX(idencol) FROM JH`），
前缀 `BILLNOLEFT2` 仍可先读（它不参与竞态）：

```python
    conf = db.q1(cur, "SELECT ISNULL(BILLNOLEFT2,'') FROM No_BillID WHERE BillNaID=1020")
    if not conf:
        raise ValueError("未找到进货单号配置(No_BillID/1020)")
    prefix = (conf[0] or "JH").strip()
    cur.execute("UPDATE No_BillID SET BillNoid = ISNULL(BillNoid, 0) + 1 WHERE BillNaID=1020")
    row = db.q1(cur, "SELECT BillNoid FROM No_BillID WHERE BillNaID=1020")
    if not row:
        raise ValueError("未找到进货单号配置(No_BillID/1020)")
    nid = int(row[0])
    max_icol = int(db.q1(cur, "SELECT ISNULL(MAX(idencol),0) FROM JH")[0])
    if nid <= max_icol:
        nid = max_icol + 1
        cur.execute("UPDATE No_BillID SET BillNoid=%s WHERE BillNaID=1020", (nid,))
```

★ 两处都满足「UPDATE 是事务第一条写语句」：取号之前只有参数校验与 `SELECT`
（`db.ensure_temp` 在取号**之后**，是 tempdb DDL，不冲突）。实施时要复核这一点没变。

### B. Agent 进程内锁（挡本进程，零 SQL 风险）

在 `create_bill` 外层（`sales.py:858` / `purchase.py:781`）加一把模块级锁，
把整段含 COMMIT 都包进去。销售与采购各一把，互不牵连。

```python
# 模块顶部
_CREATE_LOCK = threading.Lock()
_CREATE_LOCK_WAIT = 60.0   # 拿不到就报错，不让请求无限堆积
```

```python
    got = _CREATE_LOCK.acquire(timeout=_CREATE_LOCK_WAIT)
    if not got:
        idem.abort(token, database=dbns)
        raise RuntimeError("建单排队超时（%.0fs），请稍后重试" % _CREATE_LOCK_WAIT)
    try:
        return _create_bill_inner(...)
    except Exception:
        idem.abort(token, database=dbns)   # ★ 失败必释放占位（既有逻辑，保留）
        raise
    finally:
        _CREATE_LOCK.release()
```

作用：本进程内建单严格串行，DB 侧连锁等待都不会发生（快路径）。
A 仍要有 —— 它挡的是「多 Agent 实例 / 其它进程」这类 B 挡不住的情况。

### C.（可选）死锁 1205 重试 —— 建议同批做

A 引入了一个新的小风险：**X 锁要持有一整个建单事务**（~500~900ms），
期间触发器还会去更新 `Khdan` / `InvenFlow` / `Price_Kh`。
若 V3 桌面端此刻正好持着其中某行的锁、又反过来要 `No_BillID`，可能形成死锁（1205）。
概率很低（要求两侧正好交错），但**是我们这次新引入的**，建议就地缓解：

```python
# dispatch 或 create_bill 外层：捕获 1205 → 整单重试最多 1 次
```

### D.（可选，第二期）撞号 2627 重试 —— 兜桌面端

A+B 能挡住**我们自己的**全部并发。但 V3 桌面端取号是它自己的写法
（先 SELECT 后 UPDATE，不受我们的锁约束）：它若在我们 INSERT 前读到了旧号，仍可能撞。
彻底解决要改桌面端（做不到），只能兜：捕获 2627/2601 → 重新取号重试最多 2 次。
复杂度主要在「重试要重开事务 + 幂等占位先 abort 再 begin」，建议单独一批做。

## 7. 议题二：改单并发覆盖（与建单撞号独立，可分开做）

### 7.1 现状实测（`probe-edit-conflict.py`）

| 场景 | 结果 |
|---|---|
| **A 先后保存**：A 改第 1 行 3→5，B 接着改第 2 行 4→7 | 落库 `[3, 7]` ⇒ **A 的改动被静默回滚**；A、B **都收到"保存成功"** |
| **B 删行**：A 删掉第 2 行（剩 1 行），B 再保存手上那份 2 行 | **被删的行复活** |
| **C 真并发**：两人同时点保存、各改不同行 | 两个都返回成功 ⇒ **只有一份生效**，另一份静默丢失 |

**"正在被别人修改"这个状态根本不存在**，线上无从得知：

- 库里没有任何锁表（`sysobjects` 按 Lock/Edit/Open 查，只有 `HpdanTemp`/`JHTemplate` 这类模板表）
- `XS` 没有编辑态列（只有 `TimeInsert` / `TimeUpdate` / `UserUpdate`，都是**保存后的痕迹**）
- `bill.get` 不返回任何版本字段（探针实测输出"★ 没有"）
- V3 桌面端打开单据也不写任何标记 —— 它自己就没有这个概念

### 7.2 为什么是"整体回滚"而不是"部分合并"

`sales.update_bill` 是**整单覆盖**语义：前端提交"最终明细完整列表"，后端按 `iden_guid`
匹配——匹配到的比较后改写，没匹配到的旧行删除，多出来的当新行插入。

★ 关键：**改单会换行 guid**（"删旧行 + 建新行"）。实测同一行 guid 每次改都变：

```
b93c1a5e  →  0c380b01  →  9f59a468
```

所以后保存的人手上**全是过期 guid** ⇒ 前一个人改过的行一条都匹配不上 ⇒
被当成"要删除的旧行"删掉，前一个人的改动整体消失。

（附带影响：前端保存后必须重新拉单，否则第二次保存用的是过期 guid。这条要先确认前端有没有这么做。）

### 7.3 建议方案：内容指纹乐观锁（`revision`）

**为什么不用 `TimeUpdate` 当版本号**——实测不行：

```
XS 共 36617 张：TimeUpdate > TimeInsert 的只有 20 张，
且这 20 张的 UserInsert = UserUpdate = SYSTEM（全是 Agent 自己造的）
```

⇒ V3 桌面端改单看不出有维护 `TimeUpdate`，用它当版本号**挡不住 V3 端的改动**。

**做法**：

1. `bill.get` 新增 `revision`：由 单头关键字段（`NDate`/`ItemBh`/`BZ_XS`）+ 明细各行
   （`iden_guid`, `hpbh`, `qty`, `price`, `remark`, `gift`）+ 行数 算出的短哈希。
   ——纯内容派生，V3 改了内容它就会变，不依赖任何一端的"自觉"。
2. `salesbill.update` 新增**可选**参数 `revision`：
   - 传了且与当前不符 → 返回新错误码 `BILL_CONFLICT`，带上"当前版本 / 最后修改时间"，
     前端提示「该单已被他人修改，请刷新后重新修改」；
   - 不传 → 完全走原行为（向后兼容，V3 与老前端不受影响）。
3. 前端：改单页打开时记下 `revision`，保存时带回；收到 `BILL_CONFLICT` 弹提示 + 刷新。

**代价**：后端约 30 行（哈希 + 比对 + 错误码），前端改单页一处。不改 V3 行为。

**可选增强（更重，不推荐优先做）**：新建锁表做"编辑中"占位（进入改单页占位 + 心跳 + 超时释放）。
能提前提示"XXX 正在编辑"，但 V3 桌面端不参与 ⇒ 只挡 App 之间，还要处理超时释放与异常退出，
性价比不如指纹。

### 7.4 优先级怎么排

| 问题 | 严重度 | 用户感知 |
|---|---|---|
| 建单撞号 | 高 | **立刻报错**，用户知道失败了（但重试可能再撞） |
| 改单覆盖 | **更高** | **双方都收到"保存成功"，数据悄悄丢了** |

改单覆盖更危险（静默丢数据），但只在"真有两个人同时改同一张单"时才发生。
建议：建单撞号（议题一）先修；改单指纹（议题二）同批或紧随其后，看你要不要一次打包。

### 9.4 ★★★ 附带修复：云端总闸 `max_inflight` 2 → 24

验收时发现 6 路并发有 1 路被 `429 AGENT_BUSY`（在途 2 条）拦下。
**逐层排查证明这与取号逻辑无关**：

1. Agent 日志只有 **5 次** `salesbill.create` 成功 ⇒ 第 6 条**根本没到 Agent**，是云端拦的；
2. 线上 audit jsonl 显示该请求 `code=AGENT_BUSY, http=429, ms=2657`（等待 2.6s 后放弃）；
3. 在服务器上复现 `config.admission_for(cfg,'shiwantongda')`：
   `report 3 / print 2 / quick 16 / **_total cap = 2**`；
4. 根因：`/opt/v3cloud/cloud_config.json` **顶层第 81 行**遗留 `"max_inflight": 2`
   —— 2026-09-26 分级闸门改造把该键搬进 `DEFAULTS` 顶层（默认 **24**），
   但**线上那份配置文件没同步**；而 `admission_for` 读的是 `cfg.get("max_inflight")`
   （**cfg 顶层**，不是 `auth` 段）⇒ 拿到 2 ⇒ 总闸只有 2 个位。

**影响**：这正是「4~5 个 App 同时开单报『本地服务正忙』」的真正原因。

**修复**（用户批准）：备份 → 顶层 `max_inflight: 2 → 24` → 复核
`_total.cap = 24` → `systemctl restart v3cloud`（active）→ **复测 8 路全绿**。
